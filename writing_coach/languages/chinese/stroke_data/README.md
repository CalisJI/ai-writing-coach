# Hanzi stroke-order data

Verified stroke-order data for the Chinese learner dictionary. This is the
"verified source" that `UPGRADE_REGRESSION_RULES.md` §33 requires before the
product may show stroke order at all: every stroke path here comes from a real
glyph outline, and nothing in this directory is generated by AI.

outside the two ranges the learner-facing Han filter accepts, so no lookup can
ever reach them.

## Modification notice (Arphic Public License §2a)

Changed on 2026-08-25 by the Orena project: the upstream package's 9,574
per-character JSON files were **repacked into a different container format**.
Nothing inside a record was altered — `strokes`, `medians` and `radStrokes` are
copied through byte-for-byte from the upstream JSON. No glyph was added,
removed, reordered or redrawn.

The conversion is reproducible from the upstream package, and the script that
performs it is published with this repository:

```
python scripts/build_hanzi_stroke_pack.py             # download 2.0.1 and rebuild
python scripts/build_hanzi_stroke_pack.py --check     # verify the committed pack
```

## Format

`hanzi_strokes.pack` is the concatenation of one zlib record per character.
`hanzi_strokes.index.json` maps each character to `[offset, length]` in that
file, alongside provenance and a SHA-256 of the pack.

Splitting the two lets `stroke_order.py` hold only the ~200 KB index in memory
and read a single ~1.5 KB record per character, instead of parsing 31 MB of
JSON at import time. `--check` re-hashes the pack against the index, so a
truncated or partially committed pack fails loudly rather than serving
half a character.

A record is exactly what the renderer needs:

```json
{
  "strokes": ["M 272 567 Q 306 613 …"],
  "medians": [[[317, 812], [342, 786], …]],
  "radStrokes": [0, 1]
}
```

Coordinates live in the upstream 1024×1024 glyph space with the y-axis
inverted (the standard Make Me a Hanzi convention); the transform that maps it
onto a drawing surface is `translate(0, height) scale(1, -1)`.
